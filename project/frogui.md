# Frog UI

***디자인 시스템 기반 정적 파일(css) 스타일 프레임워크***

## 문제

Frog UI를 만들기 전에는 스타일과 스크립트가 결합된 단일 파일 컴포넌트(SFC)방식을 사용했습니다. 프로젝트 내부에선 재사용에 유리한 방식이지만 2-3개 서비스에 동일 컴포넌트를 복사해서 사용하면서 스타일의 일관성을 관리하기 어려웠습니다. 프로젝트마다 조금씩 다른 중복 컴포넌트들이 생성되었고 이런 상황이 반복되며 재사용이 불가능한 컴포넌트들이 문제가 되었습니다. 그래서 스타일링 부분을 분리해서 외부에서 관리 할 수 있도록 **디자인 시스템** 도입을 결정 하게 되었습니다. 당시 외부 디자인 시스템들은 브랜드 아이덴티티 스타일과 팀 내 개발 방식을 유지하며 도입하기 어려운 부분이 많았기 때문에 디자인 시스템을 직접 설계하고 scss 컴파일을 위한 빌드 시스템도 직접 구현하게 되었습니다.   

## 주요 특징

- 24개 UI 스타일 정의
- 프레임워크 의존도 제거
- Semantic naming 적용
- 다크모드 적용
- 반응형 디자인 적용

## 상세내용

**독립된 스타일 시스템**

처음 스타일을 분리하려고 했을 때는 아직 headless 방식이 나오기 전이고 또한 Vue 프레임워크는 SFC를 사용하고 있었기 때문에 스타일을 분리하는것이 일반적인 방식이 아니었습니다. 그럼에도 이러한 결정을 한것은 일단 스타일 분리가 컴포넌트 모듈화 이전까지 중요한 스타일링 방식 중 하나였고 Javascript 의존 없이 동작하는 디자인 시스템을 만드는 것을 목표로 했기 때문입니다. 그 결과 사용자 테마별로 컴파일된 완전 독립된 CSS 프레임워크를 만들었고, JS 프레임워크 의존도가 없기 때문에 Vue, React는 물론이고 HTML, CSS가 사용된 모든 곳에서 적용 가능한 스타일링 시스템을 만들게 되었습니다.  

**CSS 변수 기반**

정적 파일로 빌드 되면 SCSS 변수는 컴파일된 이후 값이 고정되게 됩니다. 그래서 런타임에서 토큰들을 사용하기 위한 방식으로 CSS 변수를 사용하는 방식을 적용했습니다. CSS 변수 사용으로 런타임에서 동일 스타일 내에서 테마 전환이 가능해졌습니다. 이를 위해 토큰들 중 *Color*, *Spacing*, *Radius*, *Typography style* 등을 변수화했습니다.  


**다크모드 지원**

CSS 변수를 적용하면서 동시에 다크 테마 지원을 설계하여, 다음과 같은 방식으로 테마를 적용하도록 했습니다. 일단 시스템이 적용된 사용자 환경의 테마를 'prefers-color-scheme'를 통해 실시간 상태를 확인하고 자동으로 적용될 수 있도록 합니다. 추가로 자동 방식보다 우선순위를 높인 클래스 네임을 지정해서 `.dark-theme`, `.dark`, `.dark-mode` 같이 'dark'가 포함된 클래스를 감지하여 테마를 적용하도록 했습니다.

**의미 있는 클래스**

최신 트렌드인 'utility-first' 방식은 빠른 개발과 용량 최소화 등의 장점들로 많은 개발자가 선호하고 있지만 코드 가독성 저하라는 큰 문제를 갖고 있습니다. 

``` html
<!-- utility-first(tailwindCSS) -->
<button class="relative inline-flex justify-center items-center 
gap-[0.4285714286em] text-[1em] font-normal leading-none align-baseline
cursor-pointer text-[color:var(--txt)] bg-[color:var(--bgc)] text-center 
select-none shadow-[0_0_0_1px_transparent_inset] px-[0.8571428571em] 
py-[0.5714285714em] rounded-[0.1428571429em] border-1 
hover:bg-[var(--base-color)]"
>
  Button
</button>

<!-- Frog UI -->
<button class="button round border">Button</button>
```

개발자에게 HTML 코드 가독성은 단순히 셀렉터 이름을 지정하는 것 외에도 페이지의 레이아웃을 예측하거나 특정 콘텐츠의 위치를 찾는 기준이 되는 등 개발 생산성에 영향을 미치는 부분이라고 생각합니다. 그래서 저는 semantic class 방식을 Frog UI의 중요한 개발 원칙으로 정하게 되었습니다. 

다양한 UI를 만들다 보면 자주 사용되는 단어들이 있습니다. `round`, `small`, `large`, `fluid`, `compact` 등의 주요 단어들을 지정하여 불규칙적으로 생성되는 클래스명의 범위를 제한하고 지정된 단어들은 연결되는 UI에 따라 유연하게 적용되도록 하여 제한된 단어로 전체 스타일 만들 수 있도록 설계했습니다. 

예를 들어 

```html
<button class="button compact">Compact Button</button>
<input class="input label compact" ... />
```

서로 다른 UI 엘리먼트에 동일한 클래스 `compact`를 적용하며 각각 축소된 버튼과, 축소된 입력창을 의미하지만, 적용된 스타일을 보면 각각 다른 스타일이 적용됩니다.

```css
.button.compact {
  ...
  padding: $buttonPadding * 0.5;
}
.input.compact {
  ...
  padding: $inputPadding * 0.5;
}
```
의미 있는 클래스는 특정한 용어를 학습하기보다는 화면에 그릴 대상을 텍스트로 설명하고 그 특징을 그대로 클래스로 표현하며 그림을 그리듯 코드를 만드는 Frog UI만의 방식을 만들기 위한 중요한 원칙입니다. 


**협업을 위한 문서**

Frog UI를 만든 이유 중 개발 효율성만큼 기획 및 디자인과의 협업의 효율성을 높이는 것이 큰 목표였습니다. 그래서 이전에 UI 컴포넌트 라이브러리를 만들었을 때부터 정보 공유를 위한 문서 사이트를 만들어 왔습니다. 일단 협업 팀 내에서 사용법, 스타일 예시, 시스템 용어 등을 최대한 빠르게 공유할 수 있도록 웹문서로 제작하고 *스토리북*과 같은 데이터 입력을 통해서 정보를 확인하는 개발자 위주의 방식보다 모든 설정 및 옵션에 대한 예시, 코드 등의 정보를 텍스트로 제공하여 비개발자도 쉽게 이해 가능한 방식을 만들어 최대한 활용할 수 있도록 구성했습니다. 

## 구성과 확장

시스템에서 정의된 토큰과 시멘틱 단어들을 바탕으로 24개의 컴포넌트로 구성되어 있습니다. 레이아웃(그리드 화면 구성과 입력 폼 템플릿 구성)과 버튼, 태그, 스위치, 체크박스 등의 엘리먼트 단위의 컴포넌트들을 포함하고 있습니다. 컴포넌트는 각자 설정된 값에 따라 2개 이상의 변형을 갖고 있고 디바이스에 영향을 받을 경우 반응형 스타일을 적용할 수 있도록 구성되어 있습니다. 

최근 정적인 스타일링의 단점인 엄격한 시멘틱 클래스로 인해 부족했던 스타일링을 일정 부분 utility-first 스타일링 방식을 추가했고 사용자 정의 html attribute를 활용하여 select, collapse, tabs, slider, tooltip 등의 javascript 기능을 간단하게 적용할 수 있도록 준비하고 있습니다. 

또한 Frog UI 스타일과 연결하여 UI 컴포넌트 라이브러리로 활용 가능하도록 Vue, React 프레임워크를 기반으로 하는 Headless UI 컴포넌트를 각각 만들어 배포 중입니다. 


## 결과 

Frog UI는 지난 5년여간 실무에 적용되며 초기 서비스 개발 생산성 향상에 큰 도움이 되었고, 디자인 시스템과 공용 컴포넌트 라이브러리 전체를 직접 개발하고 관리하는 과정에서 기술적으로도 크게 성장할 수 있었습니다.

디자인 시스템과 시멘틱 클래스를 적용하면서 스타일링 시스템을 체계적으로 구현하고 일관된 스타일을 유지할 수 있었으며, 팀 내 공통된 언어로 소통하게 되면서 업무 생산성도 함께 높아지는 경험을 했습니다. 스타일 분리와 Headless UI 방식을 선택한 것을 계기로 Vue뿐 아니라 React, 타입스크립트 등 프레임워크 기술과 로우레벨 JavaScript 역량까지 함께 향상시킬 수 있었던 시기이기도 했습니다.

변화하는 프론트엔드 환경에 맞춰 지금도 계속 업데이트하고 있으며, 앞으로도 트렌드를 따라가기보다는 문제를 먼저 파악하고 그에 맞는 기술적 의사결정을 내리는 설계 방식을 이어가려 합니다.
